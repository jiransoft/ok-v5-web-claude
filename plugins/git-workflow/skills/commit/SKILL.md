# Commit Skill

변경사항을 분석하여 팀 컨벤션에 맞는 커밋을 만든다.

## 절차

1. **상태 확인** — `git status`(untracked 포함), `git diff`, `git diff --cached`
2. **커밋 범위 결정** — `## 커밋 분리` 기준으로 나눌지 판단
3. **컨벤션 확인** — `## 컨벤션 우선순위`
4. **이슈키 획득** — `## 이슈키 우선순위`
5. **메시지 작성** — `## 커밋 메시지 형식`
6. **스테이징 + 커밋** — `## 스테이징 확인`. 메시지는 HEREDOC 으로 전달
7. **검증** — `git show --stat HEAD` 로 실제 커밋된 내용을 확인

## 컨벤션 우선순위

| 순위 | 출처 |
|------|------|
| 1 | `.claude/plugins.json` 의 `git-workflow.commit` 섹션 |

> 📍 경로는 **본체 레포 루트의 `.claude/plugins.json`** 이다. worktree 경로를 대상으로
> 작업 중이어도 설정은 본체에서 읽는다 — `plugins.json` 은 gitignore 대상이라 worktree 에
> 체크아웃되지 않는다. worktree 에서 찾다 실패하면 설정이 있는데도 CLAUDE.md·질문으로
> 조용히 폴백한다.

| 2 | `CLAUDE.md` 에 서술된 커밋 규칙 |
| 3 | 이 문서의 기본값 |

`commit` 섹션은 기본값과 다른 항목만 담는다. 없으면 전부 기본값이다.

| 키 | 값 | 기본 |
|----|-----|------|
| `subjectLanguage` | `ko` · `en` | `ko` |
| `issueKeyPosition` | `prefix` · `suffix` · `none` | `prefix` |

**커밋 히스토리는 참고하지 않는다.** 형식이 섞여 있어 근거가 되지 않는다.

## 이슈키 우선순위

| 순위 | 출처 | 예 |
|------|------|-----|
| 1 | `$ARGUMENTS` 에 사용자가 지정 | `OKEP-4815` |
| 2 | 현재 브랜치명 (`git branch --show-current`) | `feat/OKEP-4815` → `OKEP-4815` |
| 3 | 없음 | 이슈키 블록 생략 |

브랜치명에 숫자만 있으면(`docs/4173`) 프로젝트 키를 붙여 판단하되, 확신이 없으면 생략한다.
브랜치의 `feat/` 부분은 **type 힌트로만** 쓴다 — type 은 변경 내용으로 결정한다.

## 커밋 메시지 형식

```
[OKEP-123] <type>(<scope>): <subject>

<본문>

BREAKING CHANGE: <설명>
```

이슈가 없으면 앞 블록만 생략한다:

```
chore: 전체 플러그인 버전 일괄 업데이트
```

### 구성 요소

| 구성 요소 | 구분 | 조건 |
|-----------|------|------|
| `[OKEP-123] ` | **조건부 필수** | 이슈가 있으면 필수 · 없으면 통째로 생략 |
| `<type>` | **필수** | 항상 |
| `(<scope>)` | 선택 | 변경 범위가 특정 모듈·도메인에 한정될 때 |
| `: ` | **필수** | 콜론 + 공백 1칸 |
| `<subject>` | **필수** | 항상 |
| 빈 행 | **조건부 필수** | 본문이 있으면 |
| `<본문>` | 선택 | 판단이 개입된 변경이면 작성 |
| `BREAKING CHANGE:` | **조건부 필수** | 하위호환이 깨질 때 |
| `Co-Authored-By:` | 선택 | 본문 뒤 빈 행 다음. 자수 규칙 대상 아님 |

### 작성 규칙

| 대상 | 규칙 |
|------|------|
| subject 길이 | **한글 50자 이내** (이슈키·type·scope 제외) |
| subject 종결 | **명사형** (`~추가`·`~수정`·`~제거`) |
| subject 마침표 | 넣지 않는다 |
| subject 언어 | 한글. 코드 식별자·고유명사는 원표기 유지 (`Redis`, `TTL`, `UserService`) |
| type·scope 표기 | 영문 소문자 |
| scope 언어 | 한 저장소 안에서 통일 |
| 본문 형식 | **개조식 불릿(`-`) 목록** — 각 항목 명사형 종결. 산문 금지 |
| 본문 줄 폭 | 각 행 **한글 72자 이내** |
| 본문 줄바꿈 | 항목 단위로 끊는다. 한 항목이 72자를 넘으면 다음 행에 들여쓰기로 잇는다 |
| 본문 내용 | **왜**를 쓴다. 무엇은 subject 가, 어떻게는 코드가 말한다 |

`~했다`·`~함`·`~하였음`·`~합니다` 는 **subject·본문 모두 금지**다. `세션 오류 수정` 이 맞고 `세션 오류를 수정했습니다` 는 틀리다. 본문 불릿 항목도 같다 — `- Redis TTL 미반영 문제` 가 맞고 `- Redis TTL 이 반영되지 않았다` 는 틀리다.

### BREAKING CHANGE

**다른 코드가 의존하는 공개 인터페이스가 하위호환을 깨는 방식으로 바뀔 때** 본문 하단에 쓴다.

| 영역 | 예 |
|------|-----|
| REST API | 응답 필드 제거·타입 변경, 필수 파라미터 추가, 경로 변경 |
| 공개 코드 | 외부에서 쓰는 함수·클래스 시그니처 변경, export 제거 |
| FE 컴포넌트 | prop 이름·타입 변경, 필수 prop 추가, 컴포넌트 제거·개명 |
| FE 공용 자산 | 디자인 토큰·CSS 변수 제거, 라우트 경로 변경 |
| 저장 데이터 | localStorage·쿠키 스키마 변경, 비가역 DB 마이그레이션 |
| 설정 | 환경변수·설정 키 제거·개명 |

## type

| type | 설명 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서·주석 변경 |
| `style` | 포맷팅·공백·세미콜론. **CSS 변경이 아니다** |
| `refactor` | 동작 변경 없는 구조 개선 |
| `perf` | 측정 가능한 성능 개선 (응답시간, 번들 크기, 렌더 횟수, LCP/INP) |
| `test` | 테스트 코드 추가/수정 (단위·통합·컴포넌트·e2e) |
| `build` | 빌드·의존성 변경 (gradle, Dockerfile, package.json, lockfile, vite.config) |
| `ci` | CI/CD 파이프라인 설정 |
| `chore` | 위 어디에도 안 걸리는 잡무 (버전 범프 등) |

`style` 은 prettier·eslint --fix·ktlint 결과물 전용이다. 버튼 색상이나 레이아웃 변경은 사용자가 체감하는 변화이므로 `feat`·`fix`·`refactor` 다.

### 선택 순서

위에서부터 내려가며 **처음 걸리는 것**을 쓴다. `chore` 로 도망가지 않기 위한 순서다.

```
1. 사용자가 체감하는 동작이 바뀌었나?  → feat / fix
2. 성능 수치가 개선됐나?              → perf
3. 코드 구조만 바뀌었나?              → refactor
4. 포맷팅만 바뀌었나?                 → style
5. 대상이 문서·주석인가?              → docs
6. 대상이 테스트인가?                 → test
7. 대상이 빌드·의존성인가?            → build
8. 대상이 CI 설정인가?                → ci
9. 나머지                             → chore
```

`refactor` 와 `perf` 의 경계는 수치다. 측정해서 좋아졌으면 `perf`.

## 커밋 분리

한 커밋은 하나의 변경을 담는다. 아래 신호가 보이면 나눌지 사용자에게 제안한다.

- 성격이 다른 type 이 섞임 (기능 추가 + 무관한 리팩토링)
- 서로 참조하지 않는 모듈·도메인이 함께 변경됨
- subject 를 한 줄로 쓰려니 `및`·`+`·`·` 로 나열하게 됨
- subject 가 50자를 넘김 — 대개 여러 변경을 욱여넣은 결과다

나눌 때는 각 커밋이 **단독으로 빌드·동작 가능한** 단위여야 한다.

## 스테이징 확인

`git add` 는 관련 파일만 개별 지정한다. `git add .` 과 `git add -A` 는 쓰지 않는다.

이미 스테이징된 변경이 있으면 **그것을 존중한다** — 사용자가 의도적으로 골라둔 것으로 본다.
언스테이징 변경도 함께 커밋해야 할 것 같으면 사용자에게 확인한다.

스테이징 대상에 **의도와 다를 수 있는 파일**이 보이면 커밋을 멈추고 무엇이 왜 걸리는지 말한 뒤 확인받는다. 스스로 판단해서 제외하지 않는다 — 빠진 걸 사용자가 모르는 게 더 나쁘다.

- 자격증명·키·개인정보로 보이는 것 (파일명뿐 아니라 내용도 본다)
- 도구 산출물·임시파일 (`.DS_Store`, 스크린샷, 로그, 캐시 디렉토리)
- gitignore 는 1차 방어선일 뿐, 새로 만든 파일은 아직 안 걸려 있다

차단이 아니라 확인이다. `.env.example`, 더미 키, 의도한 산출물 커밋 등 정당한 경우가 있다.

## 예시

**좋음**

```
[OKEP-412] fix(auth): 중복 로그인 세션 제거 오류 수정

- 동시 세션 제한의 기존 세션 만료 처리에서 Redis TTL 미반영 문제
- 만료 시점을 정책 검사 이전으로 이동해 해결
```

**나쁨**

| 메시지 | 위반 |
|--------|------|
| `[OKEP-412] Fix(auth): 세션 오류를 수정했습니다.` | type 대문자 · 과거형·경어 · 마침표 |
| `[OKEP-412] chore(auth): 세션 코드 포맷팅` | type 선택 — 포맷팅은 `style` |
| `OKEP-412 fix: 세션 오류 수정` | 대괄호 누락 |
| `fix: 세션 오류 수정` (브랜치 `feat/OKEP-412`) | 이슈키 누락 |
| `feat: 세션 정리 및 로그 포맷 변경 + 문서 갱신` | 커밋 분리 필요 |

## 주의사항

- 커밋만 하고 **푸시하지 않는다**
- 변경사항이 없으면 빈 커밋을 만들지 않는다
- 커밋 메시지는 반드시 HEREDOC 으로 전달한다 (여러 줄 한글에서 따옴표가 깨진다)
- 커밋이 실패하면 출력을 그대로 보고하고 멈춘다. `--no-verify` 로 우회하지 않는다
- `--amend` 는 사용자가 명시적으로 요청할 때만 쓴다
- `$ARGUMENTS` 가 있으면 메시지 작성 시 반영한다
