# Flex Style Skill

기술 글을 플렉스 테크블로그 backend 연재(backend15~43, 2026-05~09)의 문체로 쓰거나 고친다. 규칙은 [reference/style-rules.md](reference/style-rules.md), 원문 발췌는 [reference/exemplars.md](reference/exemplars.md), 피할 것은 [reference/anti-patterns.md](reference/anti-patterns.md) 에 있다. 외부 명령은 쓰지 않고 파일 읽기·쓰기만 한다.

## --help 처리

`$ARGUMENTS`가 `--help`/`-h`이면 아래만 출력하고 종료:

```
/writing-tools:flex-style [<주제|초안 파일 경로>] [옵션] — 플렉스 테크블로그 문체로 기술 글 작성·교정
  --rewrite                      기존 초안의 사실·순서는 유지하고 문체·제목·도입·마무리만 고친다
  --series <n/m>                 시리즈 n/m화 — 제목 접두사, 이전 화 참조, "다음 화" 예고를 넣는다
  --length <short|medium|long>   목표 분량 (기본 medium ≈ 섹션 6~8개, 5,000~8,000자)
  인자가 없으면 다룰 사건·한 일·남은 한계를 AskUserQuestion 으로 묻는다.
```

## 절차

### 1. 입력 파악

- `$ARGUMENTS`에서 주제 또는 파일 경로와 옵션을 파싱한다. 경로면 Read 로 읽는다.
- 소재가 없으면 AskUserQuestion 으로 세 가지를 묻는다. (a) 출발점이 된 사건이나 증상 (b) 실제로 한 일과 결과 (c) 감수한 대가나 아직 남은 한계. 이 셋이 없으면 이 문체의 뼈대가 서지 않는다.
- 사용자가 주지 않은 사실(수치, 사례, 인용, 연구)은 만들어 넣지 않는다. 필요한데 없으면 본문에 `[확인 필요: 무엇]` 자리표시를 남기고 6단계 보고에 목록으로 올린다.
- 수치 꼬리표의 기준. 소재가 저희 팀의 경험담이면 출처 표시가 없는 수치에도 "자체 측정"·"자체 관찰" 꼬리표를 붙일 수 있다. 외부 수치(연구, 벤치마크, 다른 회사 사례)는 출처가 없으면 `[확인 필요: 출처]` 로 남긴다.
- AskUserQuestion 을 쓸 수 없는 환경(서브에이전트 위임, 배치 실행)이면 묻지 않고 부족한 소재를 `[확인 필요]` 로 남긴 채 진행한다.

### 2. 규칙과 발췌 로드

- Read 로 `reference/style-rules.md` 와 `reference/exemplars.md` 를 **끝까지** 읽는다. 발췌는 파일 뒤쪽에 있으므로 부분 읽기로 끝내지 않는다.
- 처음 쓰는 글이거나 `--rewrite` 면 `reference/anti-patterns.md` 도 읽는다. 교정은 피할 것을 아는 데서 시작한다.
- 이전 실행의 기억이나 요약에 의존하지 않고 매 실행마다 다시 읽는다.

### 3. 뼈대 잡기

- 먼저 네 가지를 확정한다. 도입 장면 한 컷(실제 사건·증상), 글 제목(서술형 문장), 섹션 제목 목록(모두 서술형 문장), 마무리 문장(한 문장 명제 또는 되묻기).
- 흐름은 style-rules.md 의 「구조」를 따른다. 문제 → 흔한 대안 기각 → 해법 → 대가·한계 → 도입 장면 회귀.
- `--length` 로 섹션 수를 잡는다. short 3~4개, medium 6~8개, long 9개 이상.
- `--rewrite` 가 아니면 뼈대(제목·섹션 제목·도입 한 줄·마무리 한 줄)를 사용자에게 보여주고 확정받은 뒤 본문을 쓴다. 뼈대가 틀리면 본문 전체가 헛일이 된다. AskUserQuestion 을 쓸 수 없는 환경이면 뼈대를 결과 맨 앞에 표시만 하고 계속 진행한다.

### 4. 본문 작성

- 기본 톤은 후기 글(backend36~42)이다. 합쇼체, 1인칭 "저희", em-dash 없음, 표·불릿 최소, 첫째/둘째/셋째는 문단으로.
- `--rewrite` 면 원문의 사실·순서·수치는 그대로 두고 문체·제목·도입·마무리만 고친다. 내용을 덧붙이거나 빼지 않는다. 뺀 것이 있으면 보고에 적는다.
- `--series n/m` 이면 제목 앞에 `[시리즈명 n/m]`, 첫 섹션에 이전 화 참조 한 문장, 글 끝에 `**다음 화** —` 예고 한 문단을 넣는다. 시리즈명은 사용자에게 받는다.
- exemplars.md 의 문장을 그대로 옮기지 않는다. 구조와 어법만 빌린다.
- 문장을 쓸 때마다 그 안의 수치·고유명·사례가 소재에 있는지 그 자리에서 확인한다. 서술을 매끄럽게 하려고 소재에 없는 세부("나머지 상품은 1초 안에 채워진다" 같은 대비용 수치)를 채우지 않는다. 이 유혹이 이 문체에서 가장 흔한 실패다.

### 5. 자가 검토

작성한 글을 처음부터 다시 읽고 아래를 점검한다. 걸린 항목은 고치고, 고친 글을 다시 읽어 같은 점검을 돌린다. 3회차에도 남으면 멈추고 남은 항목을 "자동 수정 실패"로 보고한다.

- [ ] 첫 문단이 구체적 사건·증상으로 시작하는가 (정의·일반론·배경 설명으로 시작하면 실패)
- [ ] 글 제목과 모든 섹션 제목이 서술형 문장인가 (명사구 제목이 하나라도 있으면 실패)
- [ ] 핵심 주장 자리에 "A가 아니라 B" 대조가 있는가
- [ ] 흔한 대안을 최소 하나 이유와 함께 기각했는가
- [ ] 대가·한계·미완을 명시한 문단이 있는가
- [ ] 수치마다 출처 또는 "자체 추산"·"자체 관찰" 표시가 붙어 있는가
- [ ] 마무리가 도입 장면으로 돌아와 한 문장 명제 또는 되묻기로 끝나는가
- [ ] em-dash(—)가 본문에 없는가 (시리즈 예고의 `**다음 화** —` 만 예외)
- [ ] 불릿·표·코드블록 합계가 3개 이하인가
- [ ] 합쇼체와 "저희"가 일관되고 "~에요/~거든요/~죠/~잖아요" 가 없는가
- [ ] 만들어 넣은 사실이 없고, 없는 사실은 `[확인 필요]` 로 남겼는가

### 6. 출력

- 사용자가 저장 경로를 지정했으면 Write 로 저장하고, 아니면 응답에 마크다운으로 낸다.
- 글 뒤에 짧은 보고를 붙인다. 도입 장면 한 줄, 섹션 수, `[확인 필요]` 목록, 자가 검토에서 고친 항목, `--rewrite` 에서 뺀 내용.

## 출력 형식

````markdown
# <서술형 제목>

<도입 장면 문단 — 사건·증상에서 시작>

---

## <서술형 섹션 제목>

<본문>

---

## <흔한 대안을 기각하는 섹션>

...

---

## <도입 장면으로 돌아오는 마무리 섹션>

<한 문장 명제 또는 되묻기로 끝>

*(본문의 식별자·수치는 설명을 위한 예시이며 실제 값이 아닙니다. 정량 서술은 저자 팀의 자체 관찰에 근거합니다.)*
````

마지막 면책 문구는 예시 식별자나 자체 추산 수치가 본문에 있을 때만 붙인다.

## 주의사항

- **적용 범위.** 기술 블로그 글, 기술 회고, 아키텍처·설계 설명 글에만 쓴다. 릴리즈 노트, Jira 댓글, 회의록, 커밋 메시지, API 문서, PR 본문에는 적용하지 않는다. 그런 요청이면 이 스킬을 끝내고 해당 문서의 관례를 따른다.
- **저작권.** exemplars.md 의 발췌는 문체 참고용이다. 문장을 그대로 옮기지 않고, 원문 URL 은 사용자가 인용을 원할 때만 결과물에 넣는다.
- **사실 날조 금지.** 1단계 규칙을 끝까지 지킨다. 그럴듯한 수치와 연구 인용이 이 문체의 특징이지만, 그것은 실제 관찰과 실제 출처가 있을 때만 성립한다.
- **길이 상한.** long 이라도 12,000자를 넘기지 않는다. 넘길 것 같으면 시리즈 분할을 제안한다.
